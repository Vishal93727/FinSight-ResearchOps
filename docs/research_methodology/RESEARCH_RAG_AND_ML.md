# Phase 3 — Financial Research AI & Advanced ML

## Document ingestion and provenance

The `/api/v1/documents/upload` endpoint accepts TXT, Markdown, CSV, JSON, HTML and PDF files. It enforces a configured byte limit, allow-lists file extensions, rejects unsupported/encrypted or empty documents, strips script/style content from HTML, and never executes uploaded content. The original byte sequence is SHA-256 hashed. Parsed text is stored with parser metadata; each chunk is stored with its document ID, chunk index, text hash, token count and source section. Exact duplicate files are rejected by a unique content-hash index.

Chunking is whitespace-token bounded (default 420 tokens with 60-token overlap) and preserves simple heading metadata. The default `feature_hash_v1` embedding is deterministic signed feature hashing with unigram/bigram signals, L2 normalization and 384 dimensions. It is an offline retrieval baseline, **not** a learned semantic model. An optional `sentence_transformers` provider can use a cached local SentenceTransformer model (default model name: `sentence-transformers/all-MiniLM-L6-v2`) when the `semantic` extra is installed. The document record stores provider, model identifier and vector dimensions; retrieval excludes documents created with a different provider/model to prevent mixing embedding spaces. Configure this with `DOCUMENT_EMBEDDING_PROVIDER` and `DOCUMENT_EMBEDDING_MODEL`. SQLite/local mode stores embeddings as JSON. PostgreSQL mode (`DOCUMENT_VECTOR_BACKEND=pgvector`) uses migration `0006` to add a 384-dimensional vector column with a cosine HNSW index; `scripts/backfill_pgvector_embeddings.py` copies existing JSON vectors after confirming provider/model lineage. The pgvector path is implemented but still needs a live PostgreSQL/pgvector integration run in a provisioned environment.

## Hybrid retrieval and citation contract

`hybrid_retrieve` combines lexical query-token coverage/frequency with cosine similarity from the active embedding provider, then applies maximal marginal relevance (MMR) to diversify the shortlist. An optional CPU SentenceTransformer cross-encoder can rerank the hybrid shortlist; it is selected explicitly with `DOCUMENT_RERANKER=cross_encoder`. The default feature-hash path is deterministic; candidate ties sort by document ID and chunk index. The API returns citation IDs mapped to stored chunk IDs, document IDs, chunk hashes and excerpts.

The default synthesizer is deliberately extractive. It only quotes retrieved chunks and attaches the matching citation ID to each extracted sentence. An optional `langchain_openai` synthesizer can call a configured LangChain chat model when `OPENAI_API_KEY` is provided and the `research-ai` extra is installed; its system prompt treats source text as untrusted input, requires evidence-only answers and demands citations on factual claims. Citation validation first checks that cited IDs belong to retrieved evidence, then runs a deterministic sentence-level lexical/numeric screen. Each factual sentence must carry an adjacent retrieved citation; the screen checks token overlap and requires numeric/date tokens to appear in the cited excerpt. This reduces unsupported output but is not semantic entailment, natural-language inference or proof of truth. Only actually referenced source IDs are retained in the report. Empty retrieval or failed checks produce `NO_EVIDENCE`, not an auto-approved answer.

## Research workflow and human approval

The bounded workflow checkpoints `validate_query -> retrieve_evidence -> synthesize -> verify_citations -> human_review` in `research_reports.workflow_trace` and persists a `ResearchWorkflowCheckpoint` row after each node (sequence, node/status, exact evidence IDs, bounded answer/citation recovery state and claim-check summary). A failed report can be resumed from the last committed checkpoint through `POST /api/v1/research/reports/{id}/resume`. Resume reuses the exact chunk IDs and verifies that documents remain READY and chunk/answer hashes still match; it does not re-run retrieval or silently replace evidence. This is explicit workflow-node recovery and is not LangGraph time-travel.
 The `deterministic` engine runs these stages inline by default; an optional real LangGraph `StateGraph` implementation is selected with `RESEARCH_WORKFLOW_ENGINE=langgraph` after installing the `research-ai` extra. Both paths stop at the same human-review gate. Reports with verified citations enter `AWAITING_REVIEW`; reports without sources enter `NO_EVIDENCE` and cannot be approved. Only ADMIN or RISK_REVIEWER can approve/reject, and non-admin authors cannot approve their own report. Decisions append a reviewer identity/time to the trace and emit audit events. The LangGraph and LangChain adapters are optional and their live execution remains unverified in this sandbox; neither provider can bypass citation linkage or human review.

## Supervised model evaluation

`POST /api/v1/ml/evaluations` and the queued `POST /api/v1/ml/evaluations/jobs` path require a READY Parquet market snapshot and a `FeatureSetVersion` derived from that exact snapshot. The API verifies snapshot bytes and the feature-set definition hash, materializes only declared features through the controlled OHLCV feature pipeline, and keeps `target_next_day_return` separate. A chronological no-shuffle holdout is used; scaling in the LSTM is fitted only on the training period. The immutable configuration fingerprint includes snapshot and feature-set hashes.

Supported model families are Ridge, Random Forest, XGBoost, LightGBM and a bounded CPU PyTorch LSTM. NumPy, pandas and scikit-learn are base dependencies because the Ridge and Random Forest baselines are part of the core evaluation workflow. Install the optional booster and PyTorch implementations with `pip install -e '.[ml]'` (XGBoost, LightGBM, joblib and CPU-capable PyTorch). The queue path persists job state/idempotency and retries dispatch failures using `POST /api/v1/jobs/{job_id}/retry`; workers roll back partial ORM writes before recording a terminal failure. Metrics include MAE, RMSE, R-squared and directional accuracy on the final chronological holdout only. `GET /api/v1/ml/evaluations/compare` ranks stored evaluations by RMSE when they share the same pinned snapshot and the same feature-set version. These metrics compare predictive fit; they are not strategy returns. The stored evaluation record links the dataset snapshot and feature-set version and points to the serialized model artifact. This is a research benchmark and not evidence of profitable or deployable trading performance.

The `/api/v1/ml/sentiment` endpoint supports a transparent finance-word lexicon baseline with local negation handling and an optional `finbert` provider. FinBERT lazily loads `ProsusAI/finbert` using Transformers and returns positive/negative/neutral probabilities; install `pip install -e '.[finbert]'` and cache model weights before use. The lexicon output is explicitly tagged `pretrained_model=false`; FinBERT output identifies the pretrained model. Model calibration, domain-specific validation and a broad sentiment evaluation set remain future work.

## Runtime limits and security notes

Small document uploads can still use the synchronous endpoint for local testing, but the Research Intelligence UI uses the staged Celery document-ingestion job path. Supervised evaluation can also be queued; synchronous API routes remain for controlled use/tests. Queue execution is implemented but requires live Redis/Celery/PostgreSQL to validate. The optional SentenceTransformer, cross-encoder, LangGraph, LangChain and FinBERT model weights have not been downloaded or executed in this offline verification environment. Worker concurrency/timeouts and resource limits must be configured for the deployment. Document text and embeddings are persisted in the relational database; secure backups, retention controls and encryption-at-rest must be configured by the deployment. The API accepts a `source_uri` only as provenance metadata and does not fetch arbitrary URLs, avoiding server-side request forgery in the ingestion path.
