# Phase 4 Operations — Governance, Reinforcement Learning & Paper Execution

Phase 4 connects reproducible PPO/SAC research evaluations to independent model governance and a deterministic, internal paper broker. This is a research and simulation environment only. There is no live broker adapter, no live-order endpoint, and no real-money execution path.

## 1. Runtime prerequisites

The default API/database paths can be inspected without training an RL model. To execute PPO/SAC training, install the optional RL dependencies in the same Python environment as the API and worker:

```bash
pip install -e '.[ml,rl]'
```

NumPy is a base dependency for the RL environment and feature calculations. The `rl` extra installs Gymnasium and Stable-Baselines3; the `ml` extra supplies optional XGBoost, LightGBM, joblib and PyTorch model implementations. In Docker Compose, set `PYTHON_EXTRAS=ml,pdf,rl` in `.env` before rebuilding so both API and worker images contain the same RL dependencies. For the full queued workflow, PostgreSQL, Redis and Celery must be reachable, and the data snapshot must be a READY Parquet snapshot generated by the Phase 1 ingestion pipeline.

Start the full stack using Compose:

```bash
docker compose up --build -d
```

Inspect queue health and the worker:

```bash
docker compose ps
docker compose logs -f api worker redis postgres
```

The Celery application is `app.workers.celery_app.celery_app` and its configured task queue is `finsight`. In a local environment with dependencies installed, a worker can be started with:

```bash
PYTHONPATH=src:backend celery -A app.workers.celery_app.celery_app worker --loglevel=INFO
```

Apply database changes before serving the API:

```bash
PYTHONPATH=src:backend alembic upgrade head
```

## 2. RL dataset and feature requirements

The RL endpoint accepts only canonical `date` and `close` column identifiers. The worker verifies all of the following before training:

- the selected market snapshot exists, is `READY`, and is stored as Parquet;
- the feature-set version belongs to that exact snapshot;
- the SHA-256 hash of the snapshot file matches its immutable manifest;
- the feature-set definition hash matches the stored definition;
- declared point-in-time features can be built from the snapshot's canonical OHLCV columns;
- at least 120 aligned feature/price observations remain after rolling-window warm-up and target alignment.

The next-session return target is never admitted as an RL observation. Supported observations are limited to the versioned feature catalogue. The service aligns close prices with each feature row by date and rejects non-finite or misaligned inputs.

### Training protocol

- Algorithms: PPO and SAC from Stable-Baselines3.
- Chronological split: default 70% training / 30% later out-of-sample evaluation; API bounds are 60–85% training.
- Feature scaling: mean and standard deviation are fit on training rows only; the same transform is applied to the holdout rows.
- Observation context: trailing price-return window plus selected, date-aligned features and current exposure/equity state.
- Action space: continuous long-only target exposure bounded from 0% to 100%; no leverage and no short selling.
- Execution convention: actions are applied at the current close, then the portfolio receives only the subsequent close-to-close return.
- Costs: configured commission and slippage are charged on turnover; reward includes drawdown penalty.
- Evaluation: deterministic policy actions on the later holdout interval; configuration, data hash, feature hash, metrics and artifact hash are persisted.

The minimum accepted training request is 5,000 timesteps; the API caps a request at 2,000,000. Use modest values for a first smoke test and reserve larger jobs for a worker with sufficient CPU/RAM. Training is queued; a successful HTTP response means the job was accepted, not that training has completed.

## 3. RL API and frontend

The **RL strategy lab** page is mounted in the left navigation. It allows a Quant Researcher/Admin to choose a READY Parquet snapshot, a feature-set version derived from that snapshot, PPO or SAC, and training timesteps. It can queue jobs, refresh status, retry queue-dispatch failures, inspect completed OOS metrics, and compare runs only when the data snapshot and feature-set version match exactly.

API routes (all under `/api/v1`):

| Method | Route | Permission / purpose |
|---|---|---|
| POST | `/rl/evaluations/jobs` | ADMIN/QUANT_RESEARCHER; queue PPO/SAC evaluation; idempotency key required in body |
| GET | `/rl/evaluations` | Authorized research, risk, portfolio and read-only roles; list evaluations |
| GET | `/rl/evaluations/comparison` | Same roles; filter to successful OOS evaluations with exact snapshot + feature lineage |
| POST | `/jobs/{job_id}/retry` | Job owner or ADMIN; retry a queue-dispatch failure without creating a second job |

The queue endpoint returns `202 Accepted`. A dispatch failure persists `QUEUE_FAILED`; it does not pretend that model training ran. The UI exposes retry for that state to the job owner with training permission.

## 4. Model governance lifecycle

1. A successful supervised or RL out-of-sample evaluation is registered as a `CANDIDATE` model version.
2. The API verifies evaluation lineage and hashes the model artifact when it exists under the configured data directory. A missing or mismatched artifact becomes a blocking risk finding; it is not silently marked verified.
3. A deterministic, versioned risk review evaluates required metrics, drawdown, volatility, Sharpe, observation count and artifact integrity. The result is PASS, REVIEW or REJECT; it is never overridable by an LLM or UI control.
4. An ADMIN or RISK_REVIEWER makes an independent APPROVE/REJECT decision. A model author cannot approve their own candidate. Approval is blocked unless deterministic risk is PASS.
5. Only an ADMIN can promote an APPROVED, risk-PASS candidate. A previously promoted version with the same model key is marked SUPERSEDED.
6. ADMIN can roll back a promoted version using the audited rollback endpoint.

Relevant API routes:

| Method | Route | Permission / purpose |
|---|---|---|
| GET/POST | `/governance/models` | Authorized readers list; ADMIN/QUANT_RESEARCHER register |
| GET | `/governance/models/{model_version_id}/risk-review` | Inspect deterministic decision, policy limits, findings and warnings |
| GET | `/governance/models/{model_version_id}/decisions` | Inspect reviewer decision history |
| POST | `/governance/models/{model_version_id}/decision` | ADMIN/RISK_REVIEWER; independent approval or rejection |
| POST | `/governance/models/{model_version_id}/promote` | ADMIN only; requires approval and risk PASS |
| POST | `/governance/models/{model_version_id}/rollback` | ADMIN only; audited rollback |

## 5. Paper-only execution

Create an internal paper account, select a promoted model, then submit an order using an explicit simulation reference price. The reference price is user-supplied simulation input, not a live market quote. The paper broker applies configured slippage and fee assumptions and writes order, fill, position, ledger and audit records.

Before accepting an order, deterministic checks evaluate:

- account kill-switch state;
- valid side and positive quantity/reference price;
- max order notional;
- available paper cash for buys;
- sell quantity versus existing paper position;
- post-trade gross exposure and post-trade symbol concentration.

Orders are idempotent through a unique `client_order_id` per paper account; replaying the same payload returns the existing order, while reusing the ID with a changed payload returns HTTP 409. Reconciliation rebuilds account cash, quantities and ledger totals from the fill history; only ADMIN may repair detected discrepancies. No external broker HTTP calls are made by the paper broker.

| Method | Route | Permission / purpose |
|---|---|---|
| POST | `/execution/accounts` | ADMIN/PORTFOLIO_ANALYST; create paper account |
| GET | `/execution/accounts` | Authorized account readers; list visible accounts |
| GET | `/execution/accounts/{account_id}/summary` | Authorized account readers; inspect cash/equity/exposure/positions |
| POST/GET | `/execution/accounts/{account_id}/orders` | ADMIN/PORTFOLIO_ANALYST create; authorized readers inspect |
| POST | `/execution/accounts/{account_id}/kill-switch` | ADMIN/RISK_REVIEWER; activate or deactivate only as permitted by server rules |
| POST | `/execution/accounts/{account_id}/reconcile` | ADMIN/PORTFOLIO_ANALYST/RISK_REVIEWER; inspect; ADMIN required for repair |
| GET | `/execution/accounts/{account_id}/audit` | Authorized account readers; inspect orders, fills, ledger and audit events |

The frontend explains that order entry uses simulation reference prices. The API does not accept a broker destination or live order type. Kill-switch deactivation and ledger repair are restricted to ADMIN.

## 6. Safe Phase 4 workflow

1. Ingest enough historical OHLCV data to create a READY Parquet snapshot.
2. Create a versioned feature set from that exact snapshot.
3. Open **RL strategy lab**, queue a small PPO evaluation, and monitor its job status.
4. Inspect the out-of-sample metrics and exact lineage; compare PPO/SAC only on the same snapshot and feature set.
5. Open **Model governance**, register a candidate from a successful OOS evaluation, inspect its deterministic risk review, and request independent review.
6. Have a different ADMIN/RISK_REVIEWER approve only if the deterministic review is PASS; ADMIN promotes the approved model.
7. Open **Paper execution**, create/select an internal paper account, and test small simulated orders with explicit prices.
8. Reconcile the account and inspect the append-only order/fill/ledger/audit history. Activate the kill switch to test that subsequent orders are blocked.

Never use real account credentials or live broker keys in this workflow. Do not interpret a successful RL evaluation as evidence of future returns or profitability.
